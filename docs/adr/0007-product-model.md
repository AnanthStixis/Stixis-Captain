# ADR-007: Captain as a product for many companies

- Status: Accepted 2026-11-26. Built (steps 1-5 of the product plan). Hosting model superseded by ADR-008 (one shared Captain); dedicated installs stay available.
- Related: ADR-005 (erasure), the Azure install (`deploy/opentofu/azure`), `docs/guides/`

## Context
Stixis offers Captain to many companies (for example "ABC Pvt Ltd"). Each company needs its own setup: its details, its first administrator, its users, its AI provider keys, and the tools its people will use (IDE, browser, MCP, SDKs, API, desktop). Activity and audit must be readable by people who are not engineers.

## Decisions
| Question | Decision |
|---|---|
| How companies share Captain | **A Stixis control plane plus one isolated Captain per company.** The control plane holds each company's details, status, install address and a health summary; never its AI activity or evidence. |
| Where the control plane runs | **On Stixis's own Captain install**, switched on with `CAPTAIN_CONTROL_PLANE=1`. Stixis staff sign in with Stixis SSO; role `platform-admin` (permission `companies:write`, never part of a client's `org-admin`). Company changes are recorded in Stixis's own evidence ledger. |
| How the control plane talks to an install | A **platform token** per company, generated by the control plane, stored there encrypted, placed by the installer in the install's Key Vault (`CAPTAIN_PLATFORM_TOKEN`). Only two endpoints accept it: `POST /admin/v1/platform/bootstrap` and `GET /admin/v1/platform/summary`. No token set = the endpoints do not exist. |
| First org admin | Bootstrap pushes the company details, creates the org admin (role `org-admin`) and returns a **one-time invite link** (7 days, single use, refused once SSO is on). The link is shown once to Stixis and never stored. |
| Company AI keys | **Entered on the dashboard, stored encrypted in Captain** (per-key data key, wrapped by a Key Vault RSA key; `CAPTAIN_SECRETS_KEY`). Never shown again, never in logs or evidence. |
| Adopters | The org admin ticks adopters on **Connect your tools**; downloads are **preset with the install's addresses, never a key**; each has an install-and-test guide (`docs/guides`). |
| Plain language | One wording layer (`captain/api/describe.py`) turns every event and reason code into a sentence, a result word and a "why"; a test fails if any code has no wording. Raw codes stay under "Technical details". |

## What a company's journey looks like
1. Stixis: **Companies → Add a company** (details, region, org admin) → **Download install files** (tfvars, backend settings, Helm values, platform token).
2. Stixis or the client's platform team: `tofu apply` + `helm install` (deploy/opentofu/azure/README.md); the platform token goes into the install's Key Vault.
3. Stixis: set the install's address → **Bootstrap** → send the invite link to the org admin → **Check now** shows health.
4. Org admin: sign in with the link → **Setup** (SSO, company details) → **Users**, **AI keys**, **Captain keys** → **Connect your tools** → people follow the guides and test.

## Consequences
- Isolation stays strong: a company's data, keys and evidence live only in its own install and Azure subscription.
- Each new company still needs an infrastructure install; the control plane prepares and tracks it but does not run `tofu apply` from a web page.
- Losing the control plane loses only the company list and health checks, never a company's data.

## Not built yet
- Automatic platform-token rotation (today: replace it in both places by hand).
- Pushing later profile changes from the control plane after bootstrap (the company owns its profile once live).
- A Stixis-wide view across companies beyond the health summary (deliberately: no evidence leaves a company's install).
